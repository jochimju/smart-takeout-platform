# 批量 SQL 与批量远程查询后的秒杀混合压测

> 此报告对应主表仍逐笔INSERT、尚未增加当前逐请求会话校验RPC的历史构建。最新主表批量写入同包对照及资源定位见 `../order-main-batch/report.md`，不能跨构建直接归因吞吐差异。

## 结论

在本机隔离环境以 800 次秒杀请求/秒、5 次普通下单请求/秒运行 60 秒，正式完整轮实际发出 48,001 次秒杀请求，压测器漏发 0。20,640 单成功受理并建单，27,361 次因每活动 500 笔未完成额度提前拒绝；没有已受理订单失败、未知结果或轮询超时。观察窗口数据库实际成功建单速率约 **334.1 单/秒**，依然不能称为 800 成功订单/秒。

与前一版“小批量事务＋事务外门控”的一次完整轮相比，成功数由 10,139 升至 20,640（约 2.04 倍），秒杀就绪 P95 由 4.009 秒降至 3.013 秒；但普通下单受理 P95 由 109.4 毫秒恶化到 **448.4 毫秒**。因此吞吐改善成立，普通下单性能不能算通过验收，不应只以秒杀成功数宣称整体方案已达标。

## 结果与比较口径

| 指标 | 上一版 8 笔事务＋门控 | 新版批量 SQL＋批量远程查询 |
| --- | ---: | ---: |
| 计划秒杀输入 | 800/秒 × 60 秒 | 800/秒 × 60 秒 |
| 实际秒杀请求 | 48,001 | 48,001 |
| 成功受理并建单 | 10,139 | 20,640 |
| 容量提前拒绝 | 37,862 | 27,361 |
| 数据库建单速率，去掉前 5 秒 | 164.1 单/秒 | 334.1 单/秒 |
| 秒杀订单就绪 P95 | 4.009 秒 | 3.013 秒 |
| 普通下单完成 | 301 | 300 |
| 普通下单受理 P95 | 109.4 毫秒 | 448.4 毫秒 |
| 普通订单就绪 P95 | 1.111 秒 | 1.467 秒 |
| 压测器漏发计划请求 | 0 | 0 |

新轮使用同机独立交易库、专用 RabbitMQ vhost 和 Redis 16380、专用交易/账户/商品实例；活动库存 60,000，批次上限 8、最长等待 50 毫秒、消费者 3、prefetch 10、未完成额度 500、处理截止 120 秒，与上一轮一致。先以 100/秒预热 20 秒，2,001 笔全部完成，再运行正式混合负载。普通购物车每用户一份套餐；显式不使用红包，也没有真实支付。客户端每秒轮询，因此“就绪 P95”包含最多约一秒的轮询量化误差。

新轮将 k6 秒杀虚拟用户预创建数提高至 1,600、上限提高至 2,500，以确保计划请求全部发出；上一轮上限为 1,200。这个差异及单机共用资源可能影响普通请求尾时延。每个版本仅一次正式完整轮，不能视作统计显著差异或生产容量承诺。此次复测复用了同一隔离交易库内已排空的夹具诊断活动，正式活动是全新活动，索引中已有历史假订单；与上一轮“每轮全新交易库”也不完全相同。

## SQL 与阶段证据

Prometheus 探针在两版均开启。新轮 20,640 单对应 2,585 次建单事务提交，平均 7.98 单/事务；写事务记录 43,906 次 JDBC 调用，事务外准备记录 2,585 次，合计约 **2.25 次/单**。上一版记录约 11.125 次/单，说明多行写入和批量预读确实减少数据库往返。新轮建单事务中的 SQL 执行平均摊销 1.482 毫秒/单、commit 0.993 毫秒/单、活动加锁调用 0.428 毫秒/单；这些区间不能相加，SQL 耗时已经包含锁等待。订单主表仍逐笔 INSERT 以获取生成 ID，红包占用仍逐笔进行。

建单速率取到达窗口去掉前五秒后的约 54.01 秒数据库 `SUCCEEDED` 计数差：334.10 单/秒。`20,640 / 60 = 344` 是到达窗口成功受理平均值，含短暂排空，不能冒充稳态建单速率；k6 Counter 的 `rate` 也包含排空时间。

## 一致性与夹具记录

停止专用交易服务后冻结正式活动快照：MySQL 与 Redis 剩余库存均为 39,360，用户资格/订单/成功受理均为 20,640，库存加资格为原始 60,000；活动内重复用户 0，未完成账本、未桥接受理、数据库 `ACCEPTED`、待同步缓存事件和到期待发事件均为 0。秒杀、普通建单和失败队列的 ready/unacked 均为 0。普通正式订单 300 单与客户端完成数一致。

最初一次 100/秒预热在新活动 Redis 初始化前开始，有 1,777 单受理，已排除。第二次误复用相同请求编号，触发预约表全局 `(user_id,request_id)` 唯一键，有 500 笔超时，亦已排除；两次夹具活动在正式轮前终结且队列排空。随后用新请求编号进行 2,001 单完整预热。首次 800/秒诊断轮受压测器虚拟用户上限影响，漏发 642 次，20,562 单建成，不作为完整输入结果；调整压测器后重新以新活动完成零漏发正式轮。保留原始诊断 JSON 供核查。

普通尾时延退化可能同时受到更高实际建单吞吐、同机压测器、增加的 k6 虚拟用户和观察器成本影响。新轮阶段观察器采样耗时中位数约 109 毫秒，上一轮约 15.5 毫秒，因此不能把普通尾时延退化全部归因于业务 SQL。结论是本机这一轮**实际观察到退化**，需要隔离压测器/观察器并做重复混合压测才能归因；不能忽略该结果。

专用 trade/account/catalog/Redis 已停止，专用 vhost 已删除，测试数据库与原始数据保留。业务服务和业务数据库未操作。新版源码和新账户服务批量地址接口尚未部署到业务环境。
