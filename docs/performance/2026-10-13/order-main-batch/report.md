# 资源定位、订单主表批量写入与同包对照

## 结论

完成主表多行INSERT、JDBC生成键回填及实际混合压测。最终对照两轮使用完全相同的交易、账户、商品JAR（SHA256见manifest），仅主表写入开关不同；各用全新交易库、专用vhost及空Redis。800秒杀请求/秒＋5普通下单请求/秒持续60秒，最终两轮压测器均零漏发。

| --- | ---: | ---: |
| 实际秒杀输入 | 48,001 | 48,000 |
| 成功受理并建单 | 18,278 | 20,482 |

成功数增加约12.1%，观察窗口速率增加约16.0%。两轮成功受理最终全部建成，无终态失败、未知结果或轮询超时。仍未达到每秒受理并最终兑现800个有效订单，普通下单尾时延也仍高。这是一组同机顺序对照，不能当作统计显著的生产容量结论。

## 资源定位与测试条件修正

本轮不再每两秒扫描累计受理、消息JSON及订单表计数来测速；使用有限标签Micrometer建单计数器取差，数据库只采样状态、当前连接/事务和锁等待，另采集服务、MySQL及k6的CPU、内存和I/O计数。速度取请求到达期去掉前五秒后的约52秒采样窗口；成功总数包含短暂排空，不能把总数/60或k6 Counter rate当成同一口径。

| 交易进程平均使用逻辑核心数 | 3.81 | 4.19 |

本机有20个逻辑处理器。数据没有显示持续的整机CPU满载，但新轮有接近满载的采样；k6、其它进程和服务在同一台机器，不能排除共享资源影响。连接池active/max指标没有暴露，记录为缺失；数据库连接/事务数量不能冒充应用连接池等待指标。Windows磁盘计数及MySQL文件I/O汇总是机器/实例级数据，不能直接归因给秒杀；InnoDB log_waits及buffer_pool_wait_free没有增长，不足以证明磁盘没有延迟。基线数据文件misc操作平均约5.75ms、redo misc平均约1.35ms，misc包含多种文件操作，不应一律称为fsync延迟。

可信对照前发现了两个实际干扰：共享target目录被其它构建清理，且当前源码已增加共享鉴权模块。于是将源码固定到独立构建目录，重新测试打包，两轮用同一包切换写入方式。新鉴权要求JWT会话标识jti，旧的压测令牌不满足要求；更新专用测试令牌，并为actuator查询使用内部认证。新鉴权还逐请求调用账户服务检查会话，因此不能与早先未包含该模块的334或416单/秒测试直接作因果比较。

保留当前鉴权的高压诊断轮（base4）实际出现Feign `java.net.BindException: Address already in use`，大量会话校验失败。该轮只建成9,712秒杀单、179普通单，不纳入优化对照。固定包使用的Feign传输未包含feign-hc5适配器；最终两轮均在启动时设置相同的JDK HTTP复用参数 `-Dhttp.maxConnections=512 -Dhttp.keepAlive=true`，并保留会话校验RPC。最终两轮无上述BindException且所有48000左右请求均归为成功受理或容量拒绝。由此可确定出站连接问题是真实限制之一；这是隔离测试启动参数，业务启动脚本没有自动改动，也不是已完成生产HTTP客户端池化部署的证据。

## 同活动串行临界区仍是重要限制

| 每成功批次阶段平均值 | base5 | new |
| --- | ---: | ---: |
| 批次全程，含门控等待 | 61.041 ms | 51.094 ms |
| 事务外writer_gate_wait | 35.128 ms | 28.492 ms |
| 全程减门控等待，近似门控持有时间 | 25.912 ms | 22.602 ms |
| 平均成功订单/commit | 7.909 | 7.875 |
| JDBC commit调用 | 8.333 ms | 8.027 ms |
| 活动行加锁调用 | 3.601 ms | 3.638 ms |

实例内同活动写入只有一个门控许可，实际事务仍持有同一活动行锁直到提交。门控将等待移到了数据库之外，所以锁等待采样少不能排除同活动串行限制。用平均每批订单数除以近似门控持有时间得到约305/348单每秒，与实测307/356较接近，支持“同活动串行写入与提交时长限制吞吐”的判断；这个估算是均值模型，不是容量上限证明。SQL执行、活动锁等待和commit区间也不能重复相加。

本次没有实现库存分桶。下一步是否需要分桶，应在同包下比较更大的受控批次，或对门控/数据库等待做专门实验；同时处理逐请求会话RPC和普通下单的共享资源压力。现有结果不能保证仅增消费者或扩排队额度就能达到800单/秒。

## 实现、测试与一致性

`OrderMapper.insertSeckillBatch`使用多行INSERT及MyBatis/JDBC generated keys，将实际ID写回对应Orders对象。服务先取得全部ID，验证插入行数、非空和唯一性，再关联明细及逐笔占用红包。没有用首ID加偏移推算，也没有放宽唯一资格或库存条件。主表、库存、资格、明细、红包占用、成功状态与outbox仍在同一事务；错误先整批回滚再按原规则拆分。普通下单仍调用原主表单笔insert。

`sky.seckill.order-batch-enabled=true`为默认；false只让秒杀批量事务中的主表恢复逐笔INSERT，保留其它批量SQL及MQ链路。该开关同时提供本轮同包基线，和回退新主表写入的路径。

独立源码快照构建共98项测试通过、30项按集成条件跳过，0失败/错误；其中23项真实MySQL测试通过。订单和明细Mapper在这些测试中已经使用真实生产XML，不再用Mock替代主表写入；16条多行插入验证每个返回ID和实际订单号、用户、金额及明细一致。还覆盖重复消费、整批回滚、拆批、库存不足、截止过期、红包订单ID关联及开关回退。

冻结对账：base5正式活动Redis/MySQL剩余库存均41,722，有效资格/订单18,278；new均39,518，有效资格/订单20,482。两轮均原始库存60,000，重复用户0，outstanding、待桥接任务、数据库ACCEPTED、缓存同步事件及到期待发事件归零，建单和失败队列ready/unacked为0。普通正式订单数量与客户端完成数一致。未执行真实支付或红包高争用负载。

两轮k6都预创建2500秒杀VU、最多4000，以确保正式输入零漏发。20秒100QPS预热存在压测器动态VU调度漏发：base5实际1947单、new1887单，均全部建成；没有把预热计入正式指标。早先base漏发123次、base2使用旧鉴权包、base4出现连接故障，均只保留为诊断数据。只有base5和new是本表同包比较。

所有专用服务/Redis已停止，专用vhost已删除，测试库和脱敏原始指标保留，未重启业务服务或给业务库执行迁移。本轮仅增加应用写入方法及配置开关，没有新增数据库迁移。
