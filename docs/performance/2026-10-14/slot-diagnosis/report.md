# 500 个秒杀处理名额停在哪个阶段

## 结论

两轮同配置诊断中，采样占用名额的 **88%～93% 在桥接及建单完成之前**，终态待 Redis 释放约 **7%～12%**。不能把当前低吞吐主要归因于完成回写，更不能继续直接归因于旧的单活动库存行锁。

目前最明确的耗时证据是 **消费者事务提交、桥接批量写库，以及发布/确认的共享串行协调**。其中事务提交的客户端耗时已经测到；发布协调有源码及任务总耗时证据，但其锁等待、领取事务、发送和确认落库尚未分开。没有证据认定某一种磁盘、Redis 或 RabbitMQ 已达到物理极限。

本轮没有更改业务处理逻辑、配额、消费者数量或数据库全局参数。只新增只读诊断工具 `tools/seckill-slot-observe.py`，复用上一轮已验证运行包，并以隔离配置恢复每批 8 单。

## 名额如何归类

先以只读 Lua 原子读取 Redis outstanding（最多 500 项）、受理总数和未桥接命令数，再按这些订单号主键查询 MySQL 接受状态：

- **未桥接**：Redis 仍占名额，MySQL 尚无该接受记录。
- **待建单**：MySQL 为 ACCEPTED，包含待发布、待消费、准备中及事务尚未提交；不能全部称为 RabbitMQ 排队。
- **终态待释放**：MySQL 已为 SUCCEEDED/FAILED/CANCELLED，最初 Redis 快照仍占名额。

Redis 与后续 MySQL、MQ 不是分布式原子快照；采样期间状态可能前进。保存采样耗时和数据库采样偏移，不把比例当成每个请求的精确时延分解。速率中的 released 来自 accepted-outstanding，仅用于本轮没有取消/过期清理的活动；失败释放也算释放，不能泛化为成功建单速率。

消费者实际平均每批约 6.64 / 6.47 单，未达到上限 8。消费计时从业务处理开始，不包含容器聚批等待；配置有 50ms 聚批等待，但本轮没有直接测量其实际耗时，不能把配置值机械加进每批耗时。

消费者 commit 约占事务总耗时 56% / 61%，订单主表写入只有约 2.5～3.4ms；因此单独继续优化订单主表 INSERT，并没有证据能直接填补到 800 单/秒。JDBC commit 耗时包含数据库提交、网络及客户端调度，不能直接称为 fsync 时间。

源码中 `MqFailMessageRetryTask.publishClaimed` 和 `flushSeckillConfirmations` 共享同一实例的 synchronized 锁，临界区包含数据库事务；发布还在锁内遍历发送。发布任务同时有 100ms fixedDelay，确认落库有 50ms fixedDelay。八桶并行没有消除这段共享串行协调。任务均值已明显高于名义调度间隔，但任务计时包含锁等待等因素，不能把它全部归为 Broker 确认时间，也不能把两个任务均值相加后推算上限。

## 资源证据与下一步

复测负载期间的一次资源采样：交易数据库 active=11/32、pending=0，Feign leased=2、pending=0，账户数据库 pending=0，未观察到该测试库的行锁等待。仅一次采样不能排除其它瞬间等待，也不能证明连接池永远充足。

MySQL 查询确认 innodb_flush_log_at_trx_commit=1、sync_binlog=1、log_bin=1。提交涉及持久化成本是合理怀疑；归档的 performance_schema 文件等待是整个 MySQL 实例的累计值，不能归因到本轮或用来证明磁盘已饱和。没有修改这些持久化参数。

下一步定位优先级：

1. 把发布协调继续细分为进入共享锁前等待、领取事务与 commit、发送循环、Broker 确认到达、确认落库及 commit。结合待建单订单的发布状态，区分发布前等待与消费者处理等待；status=3 仅表示租约已领取、确认未落库，不代表 Broker 尚未收到。
2. 在相同负载下取得 MySQL 提交与磁盘延迟的区间增量及线程等待证据，判断提交慢的具体原因。共享实例上的全局累计值不能代替归因。
3. 再决定是否缩小发布锁范围、减少消息状态持久化提交次数，以及调整聚批节奏。保持可靠投递、事务、幂等和库存账约束；本轮没有实施这些性能改动。

不建议用增加 500 配额、延长 120 秒期限或继续盲目增加消费者来替代上述定位。

## 正确性与清理

停流排空后冻结专用交易进程：两个活动分别 SUCCEEDED 32769 / 27597，MySQL 与 Redis 剩余库存分别 27231 / 32403，一人多份有效资格为 0，每桶 remaining+activeReservation=stock，outstanding、未桥接及待回写均为 0。

随后停止专用账户、商品、Redis 进程，删除专用 RabbitMQ vhost；保留测试数据库和脱敏结果供复核，没有重启业务服务或修改业务库。工具通过四种状态分类的本地校验，并完成两轮隔离实测；业务逻辑未变，没有重复执行完整业务测试套件。
