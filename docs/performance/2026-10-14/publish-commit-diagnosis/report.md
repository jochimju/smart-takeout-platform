# 发布协调与 MySQL 提交耗时定位

## 结论

这次把此前的怀疑细化成了两项实测结论：

1. **发布锁范围确实放大了等待。** 同一实例锁包住消息领取事务、逐条发送及确认状态落库。非空批次 RabbitTemplate 调用合计明显慢于解码，锁内发送阻塞确认处理；Broker 已确认的消息还要排队等后台落库。
2. **MySQL 服务端 COMMIT 自身也慢。** 独立测试库的服务端 COMMIT 均值约 52ms，与消费者 JDBC commit 的 53～55ms 同量级。不能把提交慢仅归因于 Java 调度或网络。

仍不能认定 RabbitMQ 达到容量极限，也不能认定物理磁盘已经饱和。RabbitTemplate 调用包括转换、获取/使用通道及客户端发送等；文件等待指标属于共享 MySQL 实例。已明确可优先处理的应用结构问题，不等于已证明所有底层根因。

## 改动与验证

只增加诊断，不做本轮性能优化：

- 将原 synchronized 方法改为同一对象上同范围的 synchronized(this)，把进入锁前的等待单独计时；领取、发送、确认落库仍在原锁内。
- 分别统计创建/超时消息领取，第二版区分空领取与实际领取；事务同步及 JDBC filter 记录 SQL 与 commit。
- 记录批次发送循环、解码、RabbitTemplate.convertAndSend，以及发送开始至确认回调执行的时间。回调计时不是纯 Broker RTT，包含发送、回调调度，以及发送返回后才注册回调的影响。
- 确认队列携带本机单调时间，记录确认回调入队至后台取出的等待；落库失败仍保留原结果重试，claim token 与 inFlight 结算规则保持原语义。
- 新增 tools/seckill-mysql-observe.py，以只读查询采集测试库 COMMIT digest、全实例文件等待和测试库行锁等待；没有开启/重置全局 history、计数器或修改持久化参数。

两次固定快照构建均通过相关 7 项测试（SeckillTimingTest 3 项、SeckillDeferredTimeoutTest 4 项），包括确认落库失败保留、成功后不重复结算及 Broker 失败重试。没有声称完整仓库测试全部通过。最终工具语法检查通过。

在同一 monitor 内，领取要完成数据库事务后才能发送；发送循环结束后，确认落库才有机会拿锁。确认落库期间又包含约 65ms SQL 与 62ms commit。这里存在可测量的互相阻塞；八条消费队列并不能消除它。名义 100ms 发布间隔是 fixedDelay，实际任务完成后还要再等该间隔。

**可以确定：确认排队等待明显大于本轮发送到确认回调的时间，且慢发送和确认写库共享临界区。不能因此确定：RabbitMQ 持久化吞吐已经到顶。** 下一次如需继续定位 convertAndSend 内部，应该采集发布线程的通道获取、序列化及 socket 写等待，配合 Broker 资源告警/队列指标；目前没有这份证据。

确认 UPDATE 的只读 EXPLAIN 选择 status 相关索引范围，不是已证明的全表扫描；计划是在低积压时取得，不能代替高负载执行时间分析。已归档原始计划，没有修改 SQL。

## MySQL：慢发生在服务端吗

performance_schema.events_statements_summary_by_digest 按 **SCHEMA_NAME=独立测试库、DIGEST_TEXT=COMMIT** 取区间增量：

| 指标 | 第一版 | 细分复测 |
|---|---:|---:|
| MySQL 采样窗口 | 62.01 秒 | 62.04 秒 |
| 测试库 COMMIT 次数增量 | 3934 | 4307 |
| MySQL 服务端 COMMIT 均值 | 51.60ms | 52.17ms |
| 消费建单 JDBC commit 均值 | 52.97ms | 55.32ms |

服务端 COMMIT 包含该测试库创建、桥接、确认及普通下单等事务，和消费者 JDBC 样本不是逐条匹配的对照；但服务端自身已有数十毫秒等待，这是直接证据。SUM_LOCK_TIME 不是 InnoDB 全部锁等待，不能因该字段为零排除锁。

同期全实例文件等待增量（单位为累计操作等待秒数，并非磁盘利用率）：

| 文件事件 | 第一版 | 细分复测 |
|---|---:|---:|
| binlog write | 23.91s | 21.09s |
| binlog misc | 38.48s | 33.43s |
| InnoDB data file misc | 54.58s | 46.49s |
| InnoDB log write | 2.48s | 2.86s |
| InnoDB log misc | 1.81s | 3.68s |

misc 不是专门的 fsync 计时；多个操作等待可重叠，不能将上述数值相加换算磁盘占用率。共享实例上其它数据库与后台刷页也贡献这些等待。结果提示应重点检查 binlog/数据文件持久化路径及其与提交的协调，尚不足以区分物理盘延迟、文件系统/安全软件、后台 I/O 或 MySQL 内部组提交等待。不以关闭 binlog 或降低持久化等级制造性能提升。

## 下一步的具体依据

应用侧优先评估 **拆开发布与确认结算的共享大锁，避免数据库 commit 和整批发送互相阻塞**。需要保留 inFlight 上限、claim token 防旧回调、失败重试及事务后可见性，不能直接删除 synchronized 后就上线。

数据库侧应获取 commit 高延迟时的组提交等待、操作系统对应磁盘延迟及其它负载证据，并验证消息状态领取/确认是否能减少提交次数。只优化订单主表 INSERT，不会消除已测到的提交与发布协调成本。本轮没有实施上述优化，避免把观测和优化混作因果实验。
