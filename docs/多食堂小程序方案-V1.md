# 多食堂小程序方案 V1（待确认）

> 状态：方案设计，未开始编码。  
> 范围：小程序用户端主流程，同时定义与后端、管理端的必要边界。  
> 业务定义：本期把“一餐、二餐、梅花餐厅、美食城、五餐、六餐”视为 6 个独立餐厅（门店），不引入档口拆单。

## 1. 目标

用户登录后先看到 6 个餐厅，点击某个餐厅后进入现有菜品页。现有菜品页的分类、菜品、套餐、购物车与结算交互尽量保留，但所有数据必须限定在当前餐厅。

本期成功标准不是“首页多了 6 张卡片”，而是：

1. 6 个餐厅的菜单数据不串店。
2. 购物车不能同时包含两个餐厅的商品。
3. 订单保存正确的餐厅归属和下单时餐厅名称。
4. 餐厅可以独立营业或打烊。
5. 客户端传入错误餐厅 ID 时，后端能防止串店。

## 2. 本期不做

- 餐厅内部档口独立接单、拆单与结算。
- 一笔订单同时购买多个餐厅商品。
- 类似美团、淘宝闪购的距离排序、广告竞价、个性化推荐。
- 虚构评分、虚构月销和虚构配送时效。
- 微服务拆分。

## 3. 页面导航

```text
小程序启动
    ↓
登录/自动登录
    ↓
餐厅列表页（新增）
    ├─ 一餐
    ├─ 二餐
    ├─ 梅花餐厅
    ├─ 美食城
    ├─ 五餐
    └─ 六餐
    ↓ 点击餐厅
现有菜品页（加入 restaurantId 上下文）
    ↓
购物车 → 提交订单 → 支付 → 订单详情
```

### 3.1 路由约定

- 新增：`pages/restaurant/index`
- 保留现有菜单页：`pages/index/index`
- 餐厅进入菜单：`/pages/index/index?restaurantId={id}`
- 菜单页没有合法 `restaurantId` 时，重定向餐厅列表，不加载全局菜单。
- 菜单页顶部提供“切换餐厅”，返回餐厅列表。

## 4. 餐厅列表页

### 4.1 布局

参考用户提供图片的“商家卡片列表”，但不复制大平台的广告、会员、筛选与推荐信息。

每张餐厅卡片展示：

- 餐厅图片。
- 餐厅名称。
- 位置或楼层。
- 一句简介/主营品类。
- 营业中、已打烊或暂停营业。
- 下一营业时间（后端有真实数据时再展示）。
- 起送价、配送费（各餐厅确实不同时再展示）。

### 4.2 状态表现

| 餐厅状态 | 卡片表现 | 是否可进入 | 是否可加购/下单 |
| --- | --- | --- | --- |
| `OPEN` | 绿色“营业中” | 是 | 是 |
| `CLOSED` | 灰色遮罩，显示下次营业时间 | 是 | 否 |
| `DISABLED` | 不展示 | 否 | 否 |

设计理由：打烊只是暂时不可下单，用户仍可查看菜单；禁用代表餐厅不再对用户可见。

## 5. 菜品页改造

现有页面的左侧分类、右侧菜品、套餐、口味弹窗与购物车保留。

新增的页面上下文：

```text
currentRestaurantId       当前正在浏览的餐厅
currentRestaurant         餐厅名称、图片、公告、状态等
cartRestaurantId          服务端购物车实际所属餐厅
```

菜品页加载顺序：

```text
1. 验证路由 restaurantId
2. 查询餐厅详情与营业状态
3. 查询餐厅下的分类
4. 查询默认分类的菜品/套餐
5. 查询用户当前购物车
6. 根据购物车返回值设置 cartRestaurantId
```

页面顶部显示当前餐厅名称与“切换餐厅”。结算、支付和订单页不再写死“智餐食堂”。

## 6. 状态规则

### 6.1 浏览餐厅与购物车餐厅分离

例子：

```text
购物车里有一餐商品
→ 用户可以进入二餐浏览
→ 不立即清空一餐购物车
→ 当用户准备添加二餐商品时再询问是否切换
```

这样既允许用户比较菜单，又不会在只浏览时丢失购物车。

### 6.2 跨餐厅加购

条件：

```text
cartRestaurantId != null
且 cartRestaurantId != currentRestaurantId
```

提示：

```text
购物车中已有“一餐”的商品。
加入“二餐”商品需要先清空原购物车。

[取消] [清空并加入]
```

点击“清空并加入”后，小程序调用一个服务端原子接口，由后端在一个事务中完成：

```text
校验新商品及所属餐厅
→ 清空原购物车
→ 加入新商品
→ 返回新购物车
```

不采用“小程序先清空、再发起加购”，因为第二步网络失败时用户会无故丢失原购物车。

### 6.3 切换餐厅

- 点击“切换餐厅”只返回列表，不清购物车。
- 点击另一家餐厅只切换浏览上下文，不清购物车。
- 只有确认跨店加购时才替换购物车归属。

### 6.4 打烊与禁用

- `CLOSED`：餐厅和菜单可见，加购按钮禁用，后端拒绝普通下单。
- `DISABLED`：餐厅列表不展示；通过旧链接打开时显示“餐厅暂不可用”并返回列表。
- 用户打开菜单后餐厅才打烊：页面可通过重新进入、下拉刷新或提交失败更新状态；最终以后端下单校验为准。

## 7. 购物车设计

购物车返回值不再只是商品数组，建议返回：

```json
{
  "restaurant": {
    "id": 1,
    "name": "一餐"
  },
  "items": [
    {
      "dishId": 101,
      "name": "香菇鸡腿饭",
      "number": 2,
      "amount": 14.00,
      "dishFlavor": "微辣"
    }
  ],
  "totalNumber": 2,
  "foodAmount": 28.00
}
```

购物车为空时：

```json
{
  "restaurant": null,
  "items": [],
  "totalNumber": 0,
  "foodAmount": 0
}
```

购物车角标的表现待确认：

- 推荐：全局底部购物车入口显示当前购物车件数，即使正在浏览其他餐厅。
- 打开购物车时明确显示所属餐厅，点击餐厅名可回到对应菜单。

## 8. 结算与下单

结算页不根据 `currentRestaurantId` 猜测餐厅，而是使用后端 checkout 返回的购物车归属。

结算接口建议返回：

```json
{
  "restaurantId": 1,
  "restaurantName": "一餐",
  "restaurantStatus": "OPEN",
  "foodAmount": 28.00,
  "packAmount": 2.00,
  "deliveryAmount": 3.00,
  "discountAmount": 5.00,
  "payableAmount": 28.00
}
```

提交订单时：

1. 小程序传入 `restaurantId` 作为用户意图。
2. 后端根据购物车商品反查真实餐厅。
3. 所有商品必须属于同一餐厅，且与提交的 `restaurantId` 一致。
4. 后端重新校验餐厅营业状态、商品状态、库存和价格。
5. 配送费、打包费、优惠和最终金额由后端计算。
6. 订单保存 `restaurantId` 与餐厅名称快照。

## 9. 历史订单和再来一单

历史订单卡片展示对应餐厅名称，不再统一显示“智餐食堂”。

“再来一单”流程：

```text
查询原订单
→ 取得原 restaurantId
→ 检查餐厅是否启用
→ 检查原商品当前状态与价格
→ 检查用户当前购物车是否属于其他餐厅
→ 必要时询问是否清空并切换
→ 恢复当前仍可售的商品
→ 进入原餐厅菜单或购物车
```

已下架、已删除或缺货商品不恢复，页面要告知用户。

## 10. 用户端 API 契约

| 场景 | 方法 | 路径 | 关键说明 |
| --- | --- | --- | --- |
| 餐厅列表 | GET | `/user/restaurants` | 只返回未禁用餐厅，包含当前营业状态 |
| 餐厅详情 | GET | `/user/restaurants/{restaurantId}` | 非法或已禁用时返回明确业务错误 |
| 餐厅分类 | GET | `/user/restaurants/{restaurantId}/categories` | 只返回本餐厅启用分类 |
| 菜品列表 | GET | `/user/restaurants/{restaurantId}/dishes` | 携带 `categoryId`，后端校验分类归属 |
| 套餐列表 | GET | `/user/restaurants/{restaurantId}/setmeals` | 携带 `categoryId`，后端校验分类归属 |
| 购物车 | GET | `/user/shoppingCart` | 返回餐厅信息和商品数组 |
| 普通加购 | POST | `/user/shoppingCart/add` | 服务端反查商品归属，禁止混店 |
| 跨店切车 | POST | `/user/shoppingCart/switch` | 在一个事务中清车并加入新商品 |
| 结算试算 | GET | `/user/order/checkout` | 返回购物车真实餐厅与服务端报价 |
| 提交订单 | POST | `/user/order/submit` | 服务端二次校验一车一店 |

## 11. 前端错误处理

| 后端业务错误 | 小程序处理 |
| --- | --- |
| `RESTAURANT_NOT_FOUND` | 提示餐厅不存在，返回餐厅列表 |
| `RESTAURANT_DISABLED` | 提示餐厅暂不可用，返回列表 |
| `RESTAURANT_CLOSED` | 保留菜单页，刷新为打烊状态，禁止下单 |
| `CART_RESTAURANT_CONFLICT` | 弹出跨店购物车确认框 |
| `DISH_NOT_IN_RESTAURANT` | 提示菜品信息已变更，刷新当前菜单 |
| `DISH_OFF_SALE` | 移除或标记已下架商品，重新计算购物车 |
| `PRICE_CHANGED` | 刷新 checkout 报价，让用户再次确认 |

## 12. 管理端的必要配合

本期小程序要正常使用，管理端至少需要：

- 创建和编辑 6 个餐厅的基础信息。
- 为分类、菜品、套餐指定餐厅归属。
- 单独设置每个餐厅的营业状态。
- 按餐厅筛选并处理订单。
- 后端校验管理员的餐厅数据权限，不只依靠前端选择器。

## 13. 数据模型最小集合

```text
restaurant
  id
  code
  name
  image
  description
  address
  phone
  status
  sort
  delivery_fee
  min_order_amount

category.restaurant_id
dish.restaurant_id
setmeal.restaurant_id
shopping_cart.restaurant_id
orders.restaurant_id
orders.restaurant_name
orders.restaurant_phone
```

`dish.restaurant_id` 和 `setmeal.restaurant_id` 不能仅由小程序填写；后端在创建、修改和下单时需要校验它们与分类、套餐内菜品的餐厅归属一致。

## 14. 验收场景

### 14.1 正常链路

- 登录后展示 6 个餐厅。
- 点击一餐只展示一餐分类、菜品和套餐。
- 一餐商品加车后可正常结算。
- 订单列表、订单详情和支付页都显示“一餐”。

### 14.2 串店防护

- 一餐购物车存在时可浏览二餐，原购物车不丢失。
- 加入二餐商品时弹出确认。
- 选择取消时一餐购物车不变。
- 选择清空并加入后，购物车只剩二餐商品。
- 手动篡改 `restaurantId` 与 `dishId` 组合时，后端拒绝请求。

### 14.3 状态变化

- 一餐打烊不影响其他 5 个餐厅下单。
- 菜单页停留期间一餐打烊，提交订单被后端拒绝并刷新页面状态。
- 禁用餐厅不出现在列表，旧链接也不能继续加购。

### 14.4 历史与恢复

- 餐厅后续改名时，历史订单仍显示下单时的餐厅名称。
- “再来一单”能返回原餐厅，并跳过已下架商品。

## 15. 开发顺序（确认方案后）

1. 数据库餐厅主数据和业务表归属字段。
2. 后端餐厅列表和按餐厅菜单接口。
3. 后端同店购物车、结算和下单校验。
4. 小程序原始 uni-app 工程恢复或重建。
5. 小程序餐厅列表页、菜品页上下文和跨店购物车交互。
6. 结算、支付、历史订单和再来一单改造。
7. 管理端餐厅选择、独立营业状态和数据权限。
8. 秒杀、红包、WebSocket 和统计按餐厅改造。
9. 全链路串店、越权、并发和回归测试。

## 16. 待用户确认的产品决策

| # | 决策 | V1 推荐值 | 影响 |
| --- | --- | --- | --- |
| 1 | 每次登录后是否都展示餐厅列表 | 是 | 严格符合当前设想，但老用户多一次点击 |
| 2 | 打烊餐厅是否可查看菜单 | 可查看，不可加购和下单 | 用户可预先了解菜单 |
| 3 | 切换餐厅时是否立即清购物车 | 不清，跨店加购时再确认 | 允许比较菜单，减少误清车 |
| 4 | 是否允许一单多餐厅 | 不允许 | 不引入拆单、运费分摊和多店履约 |
| 5 | 是否记住上次餐厅并自动进入 | V1 不自动进入 | 后续可作为体验优化，不影响数据模型 |
| 6 | 配送费、起送价是否按餐厅配置 | 按餐厅配置 | 影响结算报价和餐厅卡片展示 |
| 7 | 红包是全平台通用还是指定餐厅 | V1 全平台通用 | 指定餐厅需增加优惠适用范围模型 |
| 8 | 秒杀是否按餐厅展示 | 是 | 活动必须继承套餐所属餐厅 |
