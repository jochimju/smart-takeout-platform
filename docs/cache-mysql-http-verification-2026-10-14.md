# 缓存可靠补偿：真实 MySQL 与 HTTP 链路验证

## 结论

隔离 MySQL 8.0.31、独立 Redis 3.2.100、实际打包启动的 account-service 与 catalog-service，共 22 项检查全部通过。
验证期间实际终止并重启 catalog-service 三次，分别覆盖待重试任务、业务已提交但尚未完成领取、任务领取租约已提交但 Redis INCR 尚未执行。
最终 12 个持久化失效任务全部完成，未完成任务为 0，HTTP 菜单返回更新后的数据库数据。

## 环境与链路

- 创建两个全新数据库，Flyway 执行源码迁移，包括真实 MySQL 上的 V3 失效任务表。未复制业务库数据、未修改原开发数据库。
- account-service 18192，catalog-service 18193，独立 Redis 16583。商品服务通过 16582 故障代理访问 Redis，代理只用于断开网络或暂停真实命令，不伪造缓存响应。
- 管理员使用隔离账号通过真实登录接口取得 Token；HTTP 业务接口走实际远程会话与权限校验。用户菜单使用隔离用户的测试签名 Token，由实际账号服务检查用户存在及会话状态。
- 请求经过 Spring Security、Controller、事务 Service、MyBatis、真实 MySQL、持久化任务执行器及真实 Redis。没有使用 mock 替代这些业务组件。
- 管理监控接口的权限授予本次隔离测试管理员；没有关闭鉴权。

## 验证结果

| 场景 | 结果 |
|---|---|
| Flyway V3 迁移 | MySQL 执行成功，历史记录 success=1 |
| 菜品、套餐 HTTP 新增 | 数据入库、任务完成、用户菜单可见 |
| 菜品、套餐 HTTP 调价 | 从 10 改为 11，数据库与已预热菜单均返回 11 |
| 实际 MySQL 任务 INSERT 失败 | 隔离数据库触发器 SIGNAL SQLSTATE 45000；调价为 99 的操作回滚，数据库保持 11；响应 HTTP 503、code=0 |
| Redis 网络断开时调价 | 两类商品均提交为 12，接口 HTTP 200、code=1；数据库保留任务及 retry_count>0 |
| 有待重试任务时终止服务 | 重启后任务仍在；网络恢复后自动处理，两个菜单均返回 12 |
| 业务已提交、任务尚未完成领取时终止服务 | 在 MySQL 暂停领取 UPDATE，确认商品已改为 13 且任务已提交，再终止实际服务；重启后任务完成，套餐菜单返回 13 |
| 已领取租约、Redis 尚未执行时终止服务 | 代理暂停真实 INCR，确认数据库任务 status=2，然后终止实际服务；重启后租约到期接管，套餐菜单返回 14 |
| 菜品停售联动套餐 | 提前缓存两个菜单，再通过 HTTP 停售菜品；关联套餐同步停售，两个用户菜单都为空 |
| HTTP 删除 | 先删除已停售套餐，再删除菜品；数据库删除和菜单空结果有效 |
| 管理监控 | outstanding=0，12 个任务均完成 |

网络恢复到任务排空的本次观测为 0.875 秒。该数值仅代表本次两个任务、短故障、本机环境，不能作为线上恢复 SLA；实际恢复还受到退避时间（最多 300 秒）、数据库故障与积压影响。

## 测试发现并修正的接口问题

首次测试中，任务 INSERT 失败后真实 MySQL 已回滚，但未处理的数据库异常进入 `/error`，最终被安全链路转换为 HTTP 401。这是错误响应分类问题，不是数据库误提交。
在 catalog-service 的 GlobalExceptionHandler 增加数据库资源故障、瞬态数据库异常及 UncategorizedSQLException 的 503 响应，返回通用错误，不泄露 SQL 或凭据。保留原有数据库约束异常处理。
新增鉴权接口回归测试验证数据库写入故障不会被误报为认证失败；CatalogSecurityTest 的 3 个测试通过，无跳过。重新打包后完整重跑上述 22 项真实链路检查，任务 INSERT 故障均返回 503。

## 验证边界

通过这些检查可以确认：在本次实际 MySQL/HTTP 场景中，失效任务与业务数据共同提交或回滚，Redis 网络故障和实际服务退出不会丢失已提交任务，恢复后菜单最终刷新。
没有验证真实生产集群、Redis 主从故障转移、MySQL 主从切换、大规模任务积压、长时间故障、网关或前端页面，以及下单/支付交易链路。这不是整个平台的上线验收，也不意味着菜单具有强一致性。
