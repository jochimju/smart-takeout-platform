# 秒杀异步下单改造（2026-10-09）

本文对应当前源码。历史 `seckill-zero-oversell.md` 是同步版本的验收记录，不能用于说明本版本行为。

## 实现链路

```text
HTTP → Redis Lua 校验活动、预扣库存、用户去重、保存请求和待处理任务
     → 返回 ACCEPTED，订单 ID 和金额为空
Redis 待处理 Hash → 后台批量桥接事务（最多 200 条受理记录 + mq_fail_message）→ 删除已持久化任务
待发消息 → RabbitMQ 秒杀队列 → 消费者事务（MySQL 条件库存扣减 + 资格 + 订单 + 明细 + 超时消息）
前端 → 秒杀结果查询 → SUCCEEDED 后进入支付页
超时事件 → 到达订单 expire_time 后后台发布 → 关闭队列 → 重判状态、支付状态及期限 → 取消回补
```

没有同步建单回退。普通下单入口、普通建单消费者保持原有实现；共享发布器只增加秒杀待发入口和秒杀后台发布。普通定时任务与秒杀后台任务分别使用 `taskScheduler` 和 `seckillScheduler`。

Redis 待处理 Hash 与预扣在同一 Lua 中写入，兼容 Redis 3.2，不依赖 Stream。桥接任务可能被多实例重复读取：数据库受理记录唯一约束保证只登记一次待发事件，数据库事务提交后才移除 Redis 任务。消息重复投递由受理记录锁和全活动用户唯一索引去重。新活动采用库存桶行锁，历史已预热活动保留活动行锁。

2026-10-13进一步改造：新增每活动outstanding Hash，Lua受理时登记，建单SUCCEEDED/FAILED同步到Redis时释放；桥接HDEL只移除commands，不释放outstanding。默认最多500笔未终结受理，容量已满在预扣库存及登记请求前拒绝，原请求幂等重放优先于容量检查。meta.outstandingCount与Hash长度相互校验；账本丢失或不一致拒绝新增受理，不自动清零。取消成功订单可回补库存，但不会重复归还已释放的排队额度。

500是本机初始排队额度，不是500 QPS，也不是全服务容量保证。额度覆盖未桥接、待发布、MQ排队、建单处理中及等待终态同步；它按活动计数，多个活动同时满额仍可能压垮共享数据库。配置应结合真实消费速率、处理截止期限、其它活动和普通下单负载，不能通过调大额度宣称吞吐提升。

秒杀建单和到期超时outbox统一由SeckillPublishStore短事务批量领取（每批200，FOR UPDATE SKIP LOCKED），每次领取分配claim_token。Broker异步确认回调只将结果放入有界在途窗口，后台最多200条一批持久化结果；令牌匹配且status=3才允许更新，过期发送回调不能覆盖重领后的状态。实例最多1000条未完成确认，数据库不可用时保留确认结果并停止继续领取，进程崩溃由持久租约恢复。超时消息无限重试；建单发送五次后标为失败，受理记录另走原建单恢复路径。通用普通订单重试器不再竞争秒杀两类消息，普通订单发送流程保留。

Redis结果/补偿事件同步独立每100ms执行，通过有界流水线执行相同 Lua 后批量删除最多200条明确成功的事件，删除匹配(order_number,state)，不能删掉并发产生的新状态。Lua完成后数据库删除失败可以安全重放。繁忙拒绝使用单独异常返回相同业务提示，以seckill_admission_rejected_total{reason="capacity"}计数，不逐条打印ERROR。

2026-10-14：同活动每批最多 200 条，共享一次独立桥接锁和事务提交，桥接不锁库存；受理记录、建单待发消息分别用多行 INSERT。重复桥接不增加消息；身份冲突拆批隔离，临时数据库异常整批保留，避免逐条重试风暴。Redis 批量 HDEL 必须在事务代理成功返回后执行；提交成功但 HDEL 失败可安全重复桥接。

秒杀消费者仅在订单事务内登记超时事件，available_at 初始值为订单的真实 expire_time，没有提交后发 MQ 或更新发布状态的回调。后台仅领取到期事件，通过 seckill.timeout 路由直接发到关闭队列；持久消息得到 Broker ACK 且无 return 才标记已发送，发送失败五秒后重试，超时事件不受建单消息五次重试上限限制。发送进程中断由两分钟租约回收恢复。关闭消费者仍按数据库订单真实截止时间和状态判断，重复消息不重复回补。

orders.expire_time 当前为 DATETIME 秒精度，秒杀建单时显式截到整秒，再用同一个值登记超时事件，避免MySQL舍入产生不同截止时间。提前关闭消息保留待支付订单，同时对恢复任务执行幂等补登记；即使之前没有任务，也能到期再关闭，DONE/FAILED任务不会被提前消息复活。此补登记修复位于共享恢复存储，不改变普通下单入口或正常延迟消息流程。

普通订单继续使用原来的超时延迟队列。秒杀改为到期后发送，避免后台发送积压又重新开始 15 分钟 TTL；后台不可用期间可能延迟关闭，不会延长数据库订单的付款资格。需要监测到期未发送数量、最老事件延迟及重试原因，可靠发送不等于保证准点关闭。

## 小批量兑现（2026-10-13）

默认启用batch-enabled=true，单笔模式仅供开关回退与性能对照，没有恢复HTTP同步建单。独立seckillBatchListenerFactory每消费者最多收集8条，最长收集50ms；单笔工厂与批量工厂为不同实例，不改变普通订单监听工厂。

批量协调器先在写事务外读取数据库权威受理快照、商品及归属校验后的地址，再按实际活动分组。每批在独立事务内只加一次活动锁，按订单号顺序锁定受理记录并重判截止/状态，一批共享提交。单笔配置仍走原单笔SQL路径。

后续同日优化：准备阶段对最多16条命令一次读取数据库受理快照，同套餐只查询一次商品服务，地址通过账户服务内部批量接口一次按 `(userId,addressId)` 校验归属。批量地址接口最多接受16项，并继续要求内部服务令牌；账户服务必须先于交易服务部署。写事务内一次按订单号排序锁定受理记录，对实际有效的N笔订单只执行一次 `remaining_stock>=N` 的MySQL条件扣减；资格、预约、明细、成功状态及缓存事件、超时待发消息分别使用批量SQL。预约记录的请求编号和参数指纹在INSERT时一并写入，不再紧接一次UPDATE。订单主表通过多行INSERT及JDBC生成键回填每个订单ID，不能根据首个ID推算后续ID；键缺失、重复或插入行数不符时整批回滚。获取全部ID后才关联明细和逐笔占用红包。批量中的确定性错误仍按原规则整批回滚后拆分，不能把批次长度直接作为扣库数量。

这次SQL与远程调用改造通过真实MySQL事务及账户归属测试；新版60秒混合压测结果见 `docs/performance/2026-10-13/bulk-sql/report.md`。上一轮 `docs/performance/2026-10-13/fulfillment/report.md` 的速率和等待时间仅适用于小批量事务版本。新版秒杀建单吞吐上升，但普通下单受理P95明显退化，不能只看秒杀指标。

主表批量写入和资源定位的最新同包对照见 `docs/performance/2026-10-13/order-main-batch/report.md`。当前源码增加了会话校验RPC，不能直接沿用更早版本的吞吐结果。最终对照保留鉴权，固定HTTP复用参数后以主表开关比较：建单速率约307→356单/秒，仍未达到800有效订单/秒。该HTTP参数仅用于隔离测试，业务启动脚本没有自动修改。

任何写入错误都先回滚整个批次。确定性业务错误递归拆批，只让坏请求明确失败；数据库暂时故障不拆成逐笔重试风暴。失败按原受理恢复规则持久化；持久化也失败则仅重入相应Broker副本。每个deliveryTag独立ACK，必须在事务代理成功返回后；ACK异常不回补已提交订单。预读的商品/地址不是跨服务分布式事务快照，数据库受理状态、截止时间和库存仍在写锁下重判。

同活动同库存桶的写事务使用实例内32条固定公平信号量分段排队，在获取数据库事务/连接前等待，释放后再兑现下一批。分桶活动每桶1个独立消费者，不同桶并行；旧队列仍可由3个消费者处理。不同活动的桶可能散列碰撞而共享等待段，不是全局分布式锁。跨实例与其它写入仍依赖MySQL锁及唯一/条件约束；该门控主要减少同桶写入竞争时占用数据库连接。worker被中断时不会启动新的写事务。

诊断增加JDBC SELECT/INSERT/UPDATE/DELETE执行时间与调用计数，默认仍关闭。consume_batch的时间按批次计，orders_created计数在同一诊断上下文中记录；事务回滚归入error，不能计为成交。writer_gate_wait属于事务外等待，transaction_setup包含这段时间，两者不可相加；JDBC SQL执行包含锁等待，不能当作纯服务器CPU。

## 防超卖与库存含义

Redis `stock` 是可受理库存，包含尚未落库的预扣；MySQL `remaining_stock` 是尚未被实际订单占用的库存。二者分别记账，消费者不是再次抢购。

单笔消费者执行 `UPDATE seckill_activity SET remaining_stock=remaining_stock-1 ... WHERE remaining_stock>0`；批量消费者仅对重判后仍有效的N笔执行 `remaining_stock=remaining_stock-N WHERE remaining_stock>=N`。影响行数不是1时不创建订单。数据库条件扣减、用户活动资格唯一约束、订单、明细、红包占用、受理成功状态和超时待发消息在同一事务中提交。

活动自然到期不影响此前已受理的预留；成交价格使用 Lua 从活动缓存取出的价格快照。红包在实际建单时占用，红包变化或前端金额不一致会明确失败，不静默提高付款金额。付款期限从实际建单时间起算 15 分钟。

限购沿用现有取消规则：同用户同活动只能持有一份有效资格；取消释放后允许以新 requestId 再抢，并非终身只能购买一次。

## 失败、重试与取消

- 同用户、同活动、同 requestId、同参数返回原受理；参数指纹冲突拒绝，不重复扣库存。
- 确定性业务错误更新受理状态为 FAILED，同时登记 Redis 补偿事件。
- 暂时不可用、数据库错误保存有限重试依据；保存也失败时保留 Broker 副本。
- 建单成功后 ACK 失败不会触发失败补偿；重新投递看到终态直接结束。
- 数据库受理不存在的孤立消息进入现有失败死信队列，不无限重入秒杀队列。
- 默认处理期限 120 秒；后台按数据库截止时间将超期 ACCEPTED 转为 FAILED。失败和建单使用相同锁顺序，迟到消息不能复活请求。
- Redis 回补按订单号和用户当前预留编号校验，并保存订单级释放标记，重复补偿不加库存，旧补偿不删除新资格。
- 已建单取消继续在订单事务内恢复数据库库存、释放资格，再登记持久化 Redis 回补事件。
- 发现数据库库存兜底拒绝时，补偿工作器暂停该活动的 Redis 受理，等待核对，避免持续放出错误名额。

## 缓存初始化与管理限制

使用独立 `seckill:v3:{activityId}:` 前缀，所有活动键同槽。初始化先写 ready=0，数据库提交 async_initialized=1 后才开放受理。

运行中的键不设置自动过期；旧的十分钟 TTL 和按数据库每次/定时覆盖 Redis 库存已移除。定时任务仅初始化新活动和检查就绪情况，不重置实时库存。

初始化后库存缓存缺失时拒绝受理，不自动按数据库重新放量。完整初始准备已完成、但启用回调未执行的 ready=0 状态可以重新启用；缓存丢失、初始化不完整等情况仍拒绝恢复。

当前版本对已预热活动采用不可变配置：允许停用，禁止直接改价格、时间、套餐、库存或删除；要修改须创建新活动。停用先关闭 Redis 受理，已经受理的任务仍可兑现。停用请求同时提交其他字段时只执行停用，原活动配置保留。

人工恢复必须停止该活动受理及消费者，核对订单、数据库受理记录、Redis 待处理任务及补偿事件。不能只用数据库剩余库存覆盖 Redis，也不能在线清空 users/requests/released。完整 Redis 数据丢失可能丢失尚未桥接的受理，不能宣称任意故障下不丢单。

## 接口

- `POST /user/order/seckill/submit`：返回 OrderSubmitVO，新增 `submitStatus`、`failureMessage`。
- `GET /user/order/seckill/result?requestId=...&activityId=...`：查询当前登录用户的请求。前端必须传 activityId，才能在数据库桥接之前查询 Redis 受理记录；省略时只兼容数据库/历史订单查询。
- ACCEPTED：继续查询，不能支付。
- SUCCEEDED：使用真实订单 ID 和最终金额进入支付。
- FAILED / CANCELLED：展示原因，为用户下一次主动提交生成新请求编号。
- 未查询到记录或客户端轮询超时：保留原 requestId，继续查询/重试，不认定建单失败。

小程序已修改 `project-rjwm-weixin-uniapp/pages/order/index.js` 和 `pages/api/api.js`。普通订单仍查询普通 submit-result，秒杀查询自己的 result。仓库中的 unpackage 编译产物没有手工修改，发布小程序前需重新构建。

## 部署步骤

1. 停止旧同步秒杀实例，禁止旧版和新版同时处理秒杀；备份交易数据库和 Redis。
2. 使用Flyway补齐未执行的 `V2026100901__seckill_async.sql`、`V2026101301__seckill_outbox_schedule.sql`、`V2026101302__seckill_publish_batch.sql`，后两者分别新增到期调度字段和批量领取令牌/索引。数据库需MySQL8支持SKIP LOCKED；本机真实MySQL8集成通过。不要修改已经执行的历史迁移，不要重复手工执行。停止旧实例后升级，避免旧发送器抢占新租约或提前发送未来事件。
3. 先部署包含 `/internal/account/addresses/batch` 的账户服务，再部署新交易服务；确认秒杀队列已绑定、旧队列中没有需要核对的历史孤立命令。批量建单依赖该内部地址接口，账户服务未升级时不能打开批量消费者。
4. 新活动预热后确认 Redis ready=1。首次启动会按数据库历史订单占用初始化资格和可用库存；以后不再覆盖。
5. 重新构建并发布小程序，验证 ACCEPTED → SUCCEEDED → 支付、失败提示和取消回补。
6. 监测 ACCEPTED 积压及截止失败、Redis 待处理任务数量、补偿事件数量、待发消息租约和失败死信。

已有Redis活动没有admissionReady/outstandingCount时，新受理会拒绝，不能把旧待建单直接当零。推荐停流后先用旧版把commands、数据库ACCEPTED和cache_event全部排空，核对Redis与MySQL库存/有效资格，再升级并对这些已排空活动初始化新的空outstanding账本（meta.admissionReady=1、meta.outstandingCount=0）。禁止旧版仍在受理时开启新账本；没有排空或核对不一致时保持拒绝受理，不能在线清空库存/资格键。

本次只修改源码并在随机测试库验证迁移；没有给业务库执行迁移、重启业务服务或发布小程序。

## 2026-10-14：连接池与库存分桶

交易与商品服务已引入 `feign-hc5`，正式配置 HC5 连接池，总连接默认 512、每目标默认 256、获取连接最长等待 1 秒、连接超时 1 秒、各 Feign 客户端读超时沿用原设置。关闭 HTTP 自动重试，清理过期/空闲连接，`feign.pool.leased/pending/available/max` 提供池状态指标。容量可以用 `SKY_FEIGN_MAX_CONNECTIONS/SKY_FEIGN_MAX_PER_ROUTE` 调整；连接数不是下游容量保证。

`sky.seckill.stock-buckets` 默认 8，支持 1/2/4/8。只对没有历史预留且尚未初始化的活动，在活动锁下创建固定的 MySQL 桶库存，再准备 Redis 桶库存；数据库提交后开放 Redis 受理。已初始化活动永不在线转换。Redis `stock` 保留总可用库存，新增同一 `{activityId}` 槽内的 `buckets` Hash，Lua 同时检查总账与桶账一致性，再扣总库存及选中桶库存。用户资格 Hash、请求去重和 outstanding 配额仍按整个活动共享。

Lua 按用户 ID 十进制逐位取模选择首选桶，避免大 Long 精度损失；首选桶售罄时扫描其他桶，避免剩余库存被闲置。桶号写入受理记录及任务信封，桥接覆盖客户端命令中自带的桶号。库存桶号随后保存在受理表、订单预留表和 Redis 事件表。

桥接使用独立 `seckill_handoff_lock` 行保障多实例重复桥接幂等，一次事务保存最多 200 条跨桶任务；建单消费者不访问这条锁。MQ 创建命令按 `seckill.order.bucket.0..7` 路由到八条持久队列，每条队列使用独立工厂、一个消费者、小批量建单。同一活动不同桶可并行；同桶事务锁桶行，条件 `remaining_stock >= batchSize` 扣库存，全活动 `(user_id,activity_id)` 唯一索引继续兜底。业务失败整批回滚，不减少安全校验。旧活动、旧命令继续走旧队列及活动库存账本。

取消和超时取消只回补订单预留记录中的原桶，`releaseOnce` 防止重复归还；同事务登记带桶号的 Redis 终态事件。Lua 验证桶号、请求与订单归属、总账和桶账一致性后幂等回补。活动库存展示由桶剩余库存求和，不在每笔建单时更新共享活动总库存行。发送领取事务使用 READ_COMMITTED，避免 SKIP LOCKED 范围查询的间隙锁与多路 outbox INSERT 竞争；发布确认令牌和状态条件仍保留。

部署须停止所有旧交易服务实例并排空/核对旧积压，再执行新增迁移 `V2026101403__seckill_stock_buckets.sql` 并启动全套新实例；不支持新旧桥接程序混跑后开启分桶活动。不要删除旧 Redis 库存键重建，不要直接改已预热活动 bucket_count，不要用清空资格记录迁移活动。普通订单入口与消费逻辑沿用原实现，HC5 连接池与消息表资源仍与秒杀共享。

本机压测器和服务仍在同一台电脑。正确性测试或理论并行倍数不能证明持续成功受理及最终建单达到 800 单/秒，具体验收以本轮压测报告为准。

终态回写由独立单线程 `seckillCacheScheduler` 执行，每轮最多 200 条，通过 `EVALSHA` 流水线减少 Redis 往返。每项仍运行原幂等 Lua；只删除返回 1 的事件，错误桶和不一致账本留待重试。网络异常或 NOSCRIPT 时保留整批，下一轮重新加载脚本；部分已经成功的项可安全重放。消息领取使用明确的九个合法创建路由及已有路由/状态索引，超时领取使用已有到期索引，避免 OR/LIKE 加 ORDER BY id 被优化为主键扫描。排队上限仍是 500，建单等待期限仍是 120 秒。

当前一人一单语义沿用原规则：同一活动最多一份有效购买资格，取消后删除资格、归还库存，允许重新抢购；不是同一用户在整个历史中只能产生一次订单。

桥接资格核对改为一次 HMGET，并逐项核对订单号与请求指纹；不移除不匹配任务。终态事件批量删除由参数表驱动主键点查（STRAIGHT_JOIN），保留状态条件，避免 (order_number,state) 元组 IN 导致整表扫描并锁住不相关事件。并发测试锁住不相关事件时仍可删除其余 200 项，更新为 CANCELLED 的事件不会被旧 SUCCEEDED 删除。正式默认保留 8 单小批量 SQL（支持最大 16 单；16 单试验未通过容量验收），8 个库存桶，配额 500，处理期限 120 秒。

交易和账户服务显式配置 Druid 初始/最小空闲 8、最大 32、获取连接等待 1000ms，HTTP 接入队列 1024、最大连接 4096、最大线程 256；环境变量可覆盖。`sky.jdbc.pool.max/active/idle/pending` 暴露实际池状态。每实例连接预算需与 MySQL 总连接上限、部署实例数及其它服务一起计算；池配置扩大不等于证明容量提升。最终保留每批 8 单默认值，16 单实验结果单独记录，不作为已验证的默认优化收益。
