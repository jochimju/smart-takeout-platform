# 四步可靠性与性能验收结果

本轮在当前工作区实现并测试；业务数据库未迁移，业务服务未重启。用户确认没有第二台机器，因此所有实际负载结果均为同机测试，独立机器验收保留未验证。操作流程见 [运行手册](reliability-performance-runbook.md)。

供仓库查看的验证摘要已保存在 [本轮报告目录](performance/reliability-2026-10-14/README.md)；原始本机运行目录不提交到 Git。

## 1. 故障测试与修复

- Redis 强制进程重启：AOF always 下库存预扣、待桥接命令、请求去重保留，同请求不重复扣库存；无持久化重启后拒绝自动补库存，暂停受理。不能据此声称无持久化丢失的数据已恢复。
- 桥接失败：提交前数据库失败保留 Redis 命令；提交后、Redis 删除前中断允许原批重放。真实 MySQL 并发桥接、重复消费仍由唯一约束及事务保证只产生一份受理账、订单和扣减。
- MQ 重投：真实 RabbitMQ nack/requeue 再次投递相同命令，结合真实 MySQL 多次消费验证业务幂等。
- 乱序 TTL：新固定 TTL 分档队列取代新消息的可变 message expiration；先入长消息、后入短消息时短消息先进入关闭队列。正常分档增加不足 10 秒，故障/积压不属于这个时间上界。
- 支付与超时竞争：真实 MySQL 中并发执行渠道已验收到账与超时取消；结果允许付款先获锁后正常结算，或取消先获锁后保持取消并登记退款；不能重复退库存、不能复活取消订单。
- 新分档链路完整 15 分钟测试通过：`.runtime/reliability-v4-full-ttl15.log` 包含 `FULL_TTL_PASS elapsedSeconds=900`，无额外 dispatch/watchdog 调用，到期后经 Broker TTL 与 DLX 触发取消及库存回滚。

首轮故障回归 59 项无失败、无跳过，日志 `.runtime/reliability-phase1.log`。积压治理真实 MySQL 测试 4 项通过，日志 `.runtime/reliability-phase2.log`。

## 2. 历史数据与积压治理

新增 `TradeRuntimeOperations`、管理接口、指标和任务。归档只处理已完成消息，复制到归档表后事务内删除热表记录；保留未完成/失败任务和请求幂等凭证。归档批量与保留天数受限，操作与后台任务可执行，不是只写设计。

重放只允许仍在受理期限内的失败发布消息，或失败的原可靠性任务；重放与审计原子提交。新接口严格 RBAC，记录鉴权取得的操作人，原可靠性重放接口也进入审计。FAILED、取消和过期受理不能用重放复活。

活动退役必须停用、Redis 预留排空、库存额度回收、受理/回补排空、待支付订单终结。退役后不再参与桥接/预热扫描且不能重新启用。历史订单、身份凭证和 Redis 结果仍保留，后续可按业务保留策略进一步做冷存储，不能直接按时间删除有效资格。

每 30 秒记录积压指标并输出限频 WARN，采集失败有独立可用性指标。没有配置外部消息通知渠道；指标可交给运维告警系统接入。

新增 trade 迁移 `V2026101606__runtime_governance.sql` 与 account 权限迁移 `V2026101602__runtime_permissions.sql`，均在隔离应用环境经 Flyway 执行。业务环境仍需按部署流程迁移。

## 3. 分阶段诊断

所有报告位于 `.runtime/architecture-perf/sky_arch_20261014145021_b94d`，含 JAR/脚本哈希、配置、CPU/内存、消息状态、锁等待、指标原文和数据库校验。

有效诊断样本 `arch_1ab4a7579d404a58-verification.json`：800 请求/秒、60 秒，实际秒杀建单 482.38 TPS，成功 28,334 单，普通成功 301 单、失败 0；无丢迭代、无重复资格、库存一致。

|阶段|观测平均耗时|统计单位|
|---|---:|---|
|确认结算|149.9 ms|每批|
|发布认领|144.2 ms|每批|
|桥接持久化|139.9 ms|每批|
|消费事务|88.5 ms|每批，平均约 9.7 单|
|消费事务中的 JDBC commit|36.6 ms|每批|
|商品/地址准备|5.6 ms|每批|

该轮 CPU 采样峰值 94.8%，未采样到行锁等待；不能由此排除瞬时锁等待。秒杀受理到建单提交平均 893.7 ms。早期冷启动样本出现丢迭代和远程调用错误，被验收器明确拒绝。

稳定高负载下，Outbox 认领/确认写入及桥接批处理比远程准备更突出，且数据库提交占消费事务的较大部分。单确认结算 worker、固定等待、每批最多 200 条是后续重点；不能继续仅增大待处理容量。CPU、数据库提交/持久化与动态批 SQL 的成本需要分别验证，现有样本不能断言只有一个物理瓶颈。`stage-bottleneck-summary.json` 中预算估算仅基于观测均值，不是容量证明。

关闭诊断统计后的独立一轮 `arch_44798b25c1a543a2-verification.json`：同机 800 请求/秒、60 秒，实际建单 415.81 TPS，成功 23,638 单，容量拒绝 24,363 次；普通成功 301 单，失败 0；无丢迭代，库存与资格校验通过。秒杀受理平均 35.82 ms、P95 16.64 ms，P99 1064.07 ms；平均受长尾影响高于 P95 是合法统计结果。秒杀建单等待平均 1084.6 ms，CPU 采样峰值 98.6%。

诊断与非诊断试验不是只改一个变量的重复对照：存在时段、同机资源竞争和历史测试数据累积差异，不能用 482 与 416 推导诊断开关的性能收益或损耗。正式最大容量仍应在独立压测机上固定环境并重复执行。

## 4. 统一口径、同步基线与混合缓存

验收脚本交叉核对真实订单、受理成功账、唯一资格、库存、Redis 回补；丢迭代/未知请求/未排空受理等情况会拒绝达标判定。API 平均/P95 与建单等待分别报告，不能以受理 QPS 代替建单 TPS。建单等待在成功提交后记录，回滚不计成功；其平均用本轮计数差，P95 为明确标注的滚动窗口值。

普通同步/异步对照各 50 请求/秒、30 秒、预热后执行，同样业务快照、库存和校验，两组各实际成功建单 1,501 单，无丢迭代、无失败：

|方式|HTTP 平均|HTTP P95|受理到建单提交平均|
|---|---:|---:|---:|
|异步|20.47 ms|37.28 ms|134.58 ms|
|同步对照|24.59 ms|38.39 ms|19.41 ms|

对照说明异步把等待移出受理接口，但这一低负载样本平均仅约 1.20 倍耗时差；它不是历史 350→65 ms 基线，也没有证明最大吞吐提升 3 倍。异步排队使真正建单等待更长，应同时纳入用户体验指标。报告为 `normal-baseline-comparison.json`。

菜品与套餐混合缓存对照：200 个请求、29 个参考分类、固定随机种子、80% 选择热点分类；基线 SQL 查询 501 次，缓存组 54 次，削减 89.22%。接近但未达到 90%，且不代表全平台数据库压力。报告为 `cache-mixed-verification.json`。

远端 runner、导出包和报告回传协议已实现，并在同机模拟回传中验证成功，普通 6 单成功；该测试明确不作为物理独立压测证据。无令牌、无数据库凭证的可复用模板为 `.runtime/architecture-remote-template.zip`。有实际第二台机器后，按操作手册导出本轮短期令牌包执行。

## 结论与范围

四步的代码、测试、运行流程已落地；真实独立压测依用户确认没有设备而暂未执行。现有结果仍不能写实际建单 800 TPS、历史 350→65 ms、吞吐提升 3 倍或全平台查询下降 90%。真实微信商户支付/退款联调也不在这些本机测试的验证范围。

本轮隔离服务、数据库、RabbitMQ vhost 和令牌副本已清理，报告保留。全量回归最终汇总见 `.runtime/reliability-final-regression.log`；前端 31 项、Python 验收器 2 项已通过。

全量回归覆盖 249 项后端测试：248 项通过、1 项完整 15 分钟测试按开关跳过；该项另行执行并通过，因此累计 249 项均已验证通过。最终归档/重放/退役边界、权限、提交后计时与同步入口隔离回归及构建见 `.runtime/reliability-final-package.log`。
