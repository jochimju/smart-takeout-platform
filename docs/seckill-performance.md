# 秒杀性能验证协议

执行结果见 `performance/2026-10-12/report.md`（生成后可用）。正确性测试、构建成功和接口拒绝速度不能证明简历性能指标。

## 环境与数据

使用隔离数据库、Redis、RabbitMQ vhost及专用服务实例；不得共用线上活动、库存键和队列。
同步对照版本为 Git e238c55 的秒杀实现，异步版本为当前工作区。两个版本分别部署兼容的数据库迁移及缓存，其他配置、硬件、网络路径、数据规模一致。不能通过在异步接口中人为 sleep 模拟同步基线。

每个请求使用新的测试用户及其真实地址，活动库存至少覆盖计划请求数，禁用红包自动选择。800 QPS 持续60秒至少需要48000名用户和48000份库存；先用低速短时试跑。用户文件格式为 JSON 数组：`[{"token":"测试JWT","addressBookId":"地址ID"}]`，文件含凭据，不提交Git。token所属用户必须与地址一致。

## 执行

脚本为 tools/seckill-load.js，需要 k6（当前本机未发现安装）。环境变量：USERS_FILE、RUN_ID（每轮唯一）、ACTIVITY_ID、SETMEAL_ID、CANTEEN_ID、BASE_URL、MODE=sync或async、RATE、SECONDS、TOKEN_HEADER（默认authentication）、REPORT_FILE。

采用固定到达速率，避免服务变慢时负载自动下降。先预热，随后按100、200、400、800、1000 QPS逐级测试；每级使用新活动及新用户，正式稳定窗口建议60秒以上，每轮结束等待后台排空。对照测试至少重复3轮，报告每轮结果及波动。

异步脚本默认包含真实结果轮询，不把轮询HTTP请求计入下单QPS。高并发轮询会占用压测机连接，需监测压测机CPU、网络、dropped_iterations，必要时用独立压测机及更多VU。`POLL_RESULTS=false` 可单独测试受理，随后必须独立观察 Redis 待处理任务、数据库受理记录、实际订单及补偿任务；此时脚本 completed=0 表示未轮询，不能解释成没有建单。任何认证失败、重复资格、售罄、限流、业务失败都不计成功受理。

## 指标口径

- 峰值800+：固定窗口成功受理QPS达到800，业务受理率至少99%，没有丢弃迭代，同时报告P95/P99、建单完成率、积压与排空时间。
- 350ms到65ms：同一负载下成功受理请求的平均耗时对比，同时报告中位数、P95、P99。同步响应包含建单，异步响应只包含受理，不能称为实际订单完成时间缩短。
- 吞吐提升3倍：寻找两个版本在同一错误率和延迟约束下的最大稳定成功受理QPS，异步除以同步。若说实际建单吞吐，则必须分别测实际订单提交TPS；禁止用异步受理QPS除以同步建单TPS。
- 实际建单：报告从点击提交到SUCCEEDED的平均/P95耗时、已建订单数、单位时间完成TPS、排队截止失败。k6 counter rate包含排空时间，不能与固定60秒受理窗口混用。

## 数据库及中间件核对

按专用活动统计有效订单数与资格数；确认有效订单数不超过初始库存、remaining_stock非负、同用户同活动无重复有效资格。核对成功状态与订单一一对应，FAILED不存在有效订单。记录Redis待处理数、数据库ACCEPTED数、待发消息数、MQ ready/unacked及补偿事件；结束后全部排空或明确记录残留。

记录Redis延迟与内存、MySQL锁等待/连接池、MQ消费速率、JVM CPU/GC和负载机资源。单机结果仅适用于所记录环境。未执行的数字不得写入结论；未确认建单结果的请求记为unknown。
