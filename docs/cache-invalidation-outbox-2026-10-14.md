# 缓存失效的可靠补偿

## 实现

新增 Flyway `V3__menu_cache_invalidation_outbox.sql`，在 catalog 数据库创建 `menu_cache_invalidation`。
菜品/套餐业务更新与失效任务使用同一个数据库事务。套餐在 Service 写入任务；菜品的 BEFORE_COMMIT 监听器保存任务，包括关联套餐停售。
写任务失败会阻止事务提交；业务回滚不保留任务。所有商品写路径都经此机制，移除了 Controller 的直接 Redis 失效及旧 @CacheEvict。

提交后尽力立即执行任务。Redis 或任务确认失败不再把已提交的业务更新报告为失败。持久化任务仍留在数据库，后台每秒扫描最多 100 个到期任务。
任务状态：0 等待，2 已领取，1 完成。多实例通过条件更新领取 30 秒租约，每次领取生成新的 UUID Token；确认完成与记录重试都需匹配 Token，避免旧执行器修改新执行器的任务状态。
执行器退出后，租约到期可接管；扫描或领取发生数据库异常时，下次扫描继续。记录失败状态时数据库不可用，则保留处理中任务，租约到期后恢复。

每次失败记录错误摘要和次数，退避 1、2、4…秒，最多 300 秒，无重试次数上限。重复执行 INCR 会多失效一次缓存，但不会恢复旧版本。失效已成功、确认未完成时可以安全重试。
完成记录保留 7 天，每小时删除最多 1000 条；未完成记录不按年龄删除。

读取 `GET /admin/cache/invalidations`（管理端鉴权与权限检查）可查看未完成任务数、累计重试次数和最早未完成任务创建时间。系统记录失败日志，没有配置外部告警通知。

## 验证

catalog-service 共 51 个测试通过，失败 0、错误 0、跳过 0。日志为工作区 `.runtime/cache-outbox-final-tests.log`。

- H2 MySQL 兼容模式执行实际 V3 迁移，使用真实 JDBC 事务：业务与任务共同回滚；任务插入失败回滚业务；提交后的 Redis 故障不回滚业务。
- 新执行器接管已提交待处理任务；未到期租约不接管，到期租约可恢复。
- 失效成功但确认失败可重复执行；失败状态写入数据库失败后仍能通过租约恢复。
- 两个执行器竞争时，仅一个持有有效租约并执行。
- 菜品新增/修改/删除/起停售及套餐四条写路径验证任务/版本的提交和回滚语义。
- 独立真实 Redis、Lua、序列化验证菜品与套餐：失效异常注入后仍可读到旧缓存；新执行器自动重试成功后返回新数据。
- 原旧数据回填隔离、并发重建、锁续期/所有权及权限测试保持通过。

## 部署与边界

部署新版本时由 Flyway 建表，再统一更新全部 catalog-service 实例。新旧版本混跑时，旧实例不会写入持久化任务。服务重启会重新加载定时任务，从数据库继续处理。
Redis 命令默认超时 2 秒（可通过 SKY_REDIS_TIMEOUT 设置），与数据库/线程调度耗时一起影响恢复速度；30 秒租约超时允许重复执行，重复 INCR 安全。
数据库与 Redis 同时长期不可用、任务积压或退避等待期间，菜单仍可能陈旧，Redis 不可用时读取也可能失败。这是有持久化补偿的最终一致性，没有承诺即时或强一致性。
每次全局版本失效可能引起分类缓存回源；应观察积压、重试和回源量。数据库成功提交与任务成功持久化是可靠补偿的前提。
