# 可观测性运行与验证

## 交付范围

五个服务均暴露 `/actuator/health`、`/actuator/metrics` 与 `/actuator/prometheus`。Prometheus 抓取 JVM、进程、HTTP、Spring Cloud Gateway、数据库连接池及 RabbitMQ 相关指标；指标统一附带低基数的 `application` 标签。

Micrometer Tracing 使用 OpenTelemetry 的 W3C `traceparent` 协议。HTTP 入站、Gateway 转发、Feign 调用和启用 observation 的 RabbitMQ 生产/消费会携带同一条链路；日志中的 `traceId` 可与 Tempo 查询结果关联。原有 `X-Trace-Id` 仍仅用于应用日志兼容，不应作为跨服务追踪协议。

## 启动

先启动五个业务服务，再在仓库根目录执行：

```powershell
docker compose -f observability/compose.yaml up -d
```

服务运行在宿主机时，Docker Desktop 使用 `host.docker.internal` 抓取 8080 至 8084 端口。若监控栈和业务服务都部署在 Linux Docker 网络中，请把 `prometheus.yml` 中的地址替换成对应的服务名和端口。

访问：

- Prometheus：`http://localhost:9090`
- Grafana：`http://localhost:3000`，初始账号密码均为 `admin`；请首次登录后立即修改。
- Tempo 查询 API：`http://localhost:3200`

默认 OTLP HTTP 地址是 `http://localhost:4318/v1/traces`。若 Tempo 部署到其他位置，为所有服务设置 `OTEL_EXPORTER_OTLP_ENDPOINT`；采样比例通过 `MANAGEMENT_TRACING_SAMPLING_PROBABILITY` 调整。开发环境为 `1.0`，生产建议基于容量和错误率采用较低比例。

## 验收

1. 打开任一服务的 `/actuator/prometheus`，确认有 `http_server_requests_seconds_count` 与 `jvm_memory_used_bytes`。
2. 在 Prometheus 的 Targets 页面确认五个实例均为 `UP`。
3. 经网关发起一次涉及 Feign 或 RabbitMQ 的订单流程；在 Grafana 的 Explore 中选择 Tempo，按服务名或 trace ID 查询链路。
4. 打开自动导入的“Sky Take Out / 服务总览”仪表盘，确认请求速率、P95、5xx 和 JVM 堆内存有数据。

## 边界

这版不把 `userId`、订单号、URL 参数等写入 Prometheus 标签，以防时间序列无限膨胀。业务维度（如下单成功/失败、库存不足、消息重试次数）应在后续按稳定的、有限枚举的标签单独埋点，不能用订单或用户标识作为标签。
