## 保留的设计与边界

保留 gateway/account/catalog/trade/notification 服务边界、Redis、RabbitMQ、MySQL；没有引入新的消息中间件或分布式事务框架。菜单保留 Cache Aside、预热、Redis 互斥锁及版本化键；商品修改和失效事件同事务保存，提交后失效失败由持久化事件重试。此处保证最终一致性，Redis 故障期间存在失效延迟，不能写成强一致。

库存口径为商品 SKU：菜品与套餐各有交易库存，本次没有实现原材料或套餐 BOM 级别的共同扣料。catalog 的 stock 只用于首次建账；之后补货通过交易库存调整接口，修改商品资料不能充当补货。

新秒杀活动从普通套餐库存划拨。已初始化的历史活动不会自动补扣普通库存，避免错误地二次扣减；上线前必须人工核对这部分旧账。活动剩余额度回收后保持停用；之后取消历史订单释放的库存进入普通套餐池。

一人一单指同活动最多一份有效资格。取消事务删除数据库资格，Redis 回补事件完成后允许新请求重抢；异步回补尚未完成时可能短暂提示重复购买。旧请求查询保留 CANCELLED，不能复用旧请求当新订单。

秒杀 Redis 预扣后由后台桥接到持久化受理账与 Outbox，存在 Redis 未持久化故障窗口；生产环境需配置合适的 Redis 持久化、复制、备份与故障恢复。DB 条件扣减仍是防超卖最终约束，不能把本机单 Redis 测试当成跨故障域可靠性验收。

## 新接口与迁移

`POST /admin/inventory/adjust`：`adjustmentId` 为 16–64 位稳定编号，`productType` 为 DISH/SETMEAL，`productId` 与 `delta` 指定调整；同编号同参数只生效一次，同编号不同参数拒绝。余额未建账时拒绝调整。

`POST /admin/seckill/activity/{activityId}/inventory-return`：先停用活动，再排空受理和回补；回收剩余额度。实际路由以 SeckillActivityController 为准。

trade 新迁移：V2026101601 库存流水与划拨账，1602 普通受理快照及购物车版本，1603 延时消息绝对截止时间，1604 过期发布租约索引，1605 回收状态索引。account 1601 增加新库存管理接口权限，仅 SECURITY_ADMIN 默认拥有。测试已验证新建库迁移；业务环境上线前应备份，并核对历史数据与权限。

全量后端回归日志：`.runtime/architecture-complete-regression.log`，237 项中 232 通过、5 项按开关跳过，没有失败。随后单独执行账号真实 MySQL 集成测试 4 项全部通过，日志 `.runtime/architecture-account-mysql.log`。前端 31 项通过，日志 `.runtime/architecture-frontend-resume.log`。

真实 MySQL 测试覆盖库存争抢不超卖、版本变化不补库存、调整与划拨幂等、回收与取消、普通快照及同请求并发、消息租约、支付迟到与退款边界。真实 Redis 测试覆盖预扣、去重、回补及缓存一致性；真实 RabbitMQ 测试覆盖 TTL 转死信。完整 15 分钟测试另见 `.runtime/architecture-full-ttl15.log`，最终结果应以日志中的 FULL_TTL_PASS 和测试汇总为准。

隔离压测目录：`.runtime/architecture-perf/sky_arch_20261014124531_ed19`，报告记录服务 JAR 哈希、参数、k6 原始统计、数据库建单采样和库存校验。压测与服务、MySQL、RabbitMQ 在同一开发机器上，存在资源竞争；不是生产环境容量证明。

已完成的 800 请求/秒、60 秒试验：`arch_ebfac598b0cc4395-verification.json`，实际秒杀建单约 494.86 TPS，成功 29,697 单，重复资格 0，库存 DB/Redis 相等、回补排空，普通成功 300 单、失败 0。压测丢迭代 0；待处理容量上限拒绝 18,304 次。秒杀受理平均 3.62 ms、P95 5.94 ms；普通受理平均 125.33 ms、P95 512.16 ms。不得据此声称实际建单 800 TPS、普通受理 65 ms 或吞吐提升 3 倍。

350 ms 的历史基线与相同场景 3 倍增益尚未验证。缓存热点对照采用实际 SQL digest 计数，强制每次冷读与同一分类预热读各 100 次；此实验能证明该热点场景的查询削减，不能推广成全平台数据库压力下降 90%。

进一步调参试验 `arch_9ee2a96c0efb4589-verification.json`：将待处理上限升到 2000，桥接/发布/回补间隔缩至 20 ms，确认结算间隔 10 ms，以 1000 请求/秒运行 60 秒；实际约 346.16 TPS，成功 21,264 单，普通成功 301 单、失败 0，但 k6 丢迭代 688、退出 99，不能作为达标证据。库存与唯一资格仍通过。该参数组没有写入业务默认配置。下一步应在独立压测机、固定资源配额下进行发布/消费分阶段 profiling，优先识别持久化吞吐与同机 CPU/内存竞争，而不是继续盲目增大队列。

`flow-verification.json` 为实际 HTTP 验证：同请求返回原订单、第二份资格拒绝、重复取消、取消回补后新请求重抢全部通过。`cache-verification.json` 为实际 HTTP 与 SQL digest 对照：100 次冷读 SELECT=100、100 次预热读 SELECT=0。最后一次源码构建及库存/普通快照/支付/MQ租约/超时消费者回归共 59 项通过，无跳过，见 `.runtime/architecture-final-package.log`；前端新增重试正文与换号测试，共 31 项通过。

真实微信商户、回调证书和退款渠道未开展实际交易联调；本机支付验证不等于真实交易成功。

完整 15 分钟测试最终通过：`.runtime/architecture-full-ttl15.log` 包含 `FULL_TTL_PASS`，验证订单在到期前持续待支付，到期后仅靠 Broker TTL 与 DLX 触发取消及库存回滚，无额外 watchdog 扫描；单项测试无失败、无跳过。全量回归原跳过的 5 项均已补跑成功，累计 237 项后端测试通过，前端 31 项通过。正式压测资源、独立测试库、vhost 和凭证文件已清理；保留报告及源码。
